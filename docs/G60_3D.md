# G60 component preview

The existing five sidebar tabs are preserved. The G60 model is embedded in Overview and the requirement review drawer. Other selected vehicle families display an explicit unavailable state rather than reusing the G60 mesh.

## Asset research and chosen approach

- [2023 BMW i5 M60 by Nazh Design on Sketchfab](https://sketchfab.com/3d-models/2023-bmw-i5-m60-207fd872d28b4cafa7fefe061ae98e26): search listing advertises a downloadable CC Attribution model, approximately 1.5 million triangles / 795,000 vertices. Direct page access returned 403 in this environment. No file was downloaded or bundled. This is a potential later asset, subject to download access, attribution, optimization and verifying editable interior parts.
- [BMW's 5 Series launch dimensions](https://www.press.bmwgroup.com/south-africa/article/detail/T0419079EN/the-new-bmw-5-series-sedan?language=en): 5,060 mm length, 1,900 mm width, 1,515 mm height and 2,995 mm wheelbase.
- [Three.js model loading guidance](https://threejs.org/manual/pages/loading-3d-models.html) and [OrbitControls](https://threejs.org/docs/pages/OrbitControls.html) describe the future GLB import and current camera interaction.

For this demo the bundled model is **original procedural geometry**, approximately following the G60 proportions with a sedan roofline, four doors, kidney grille, slim lights, four seats plus rear bench, dashboard and independent components. It is not a downloaded licensed BMW mesh, digital twin, engineering drawing, or exact fitted configuration. Component positions and dimensions are schematic. The underfloor battery is a charging/powertrain concept marker, not a claim that ICE, PHEV and BEV layouts are identical.

All model code is local and editable; the scene makes no asset requests to third-party sites. Replace `createG60Geometry` with a suitably licensed and optimized GLB later, retaining stable component IDs and independent display, vent and seat groups. Do not label an M4, G30, or generic sedan mesh as a production G60 asset.

## Priorities and interaction

`componentForRequirement` maps supported feature names to schematic components. Unmapped features remain unmapped and are counted in the panel. Physical proxies such as a screen for infotainment or a front sensor for driver assistance do not claim exact issue location.

For each component, use the highest priority among its current cohort requirements: critical-review flag, High, Medium, Low, then Unscored. Critical flags and High are red; Medium amber; Low green; Unscored blue; no mapped requirement grey. Critical flags are a need for review, not confirmation of a defect. Demand does not invent an impact band. The panel refetches when cohort or review version changes.

Select components by clicking the model, its hotspot labels, or the accessible component dropdown. The requirement selector focuses the corresponding component. Requirement review opens the matching 3D location. A specifically worded larger-screen/vent or adjustable-seat requirement can activate a matching concept; ordinary feature selection only highlights the area.

Demo concept values are explicit assumptions: display width +80% and height +65%; vent opening height +200% (3× baseline) and spacing +18%; front seats forward 0.38 m, up 0.20 m and additional backrest rotation 0.50 radians (~29°). These are illustrative transformations, not feasible or approved engineering changes. Baseline shows the original geometry; After restores the complete combination of accepted designs and the current preview. Reset clears the temporary preview and restores the camera, retaining saved approvals. Cyan animated bounds and ghost geometry highlight changes; priority colours stay tied to PM evidence. Camera motion respects reduced-motion settings.

The requirement approval dialog now includes an explicit 3D design selection (or no geometry change). A selected preset is saved as `design_concept` in the existing decision JSON and audit trail, scoped to the current cohort and requirement revision; no database migration is needed. Overview combines all accepted presets and restores them after reload. Rejecting, postponing or editing a requirement removes its active design; impact-band changes retain it. Previous approvals without this field remain unchanged until explicitly reviewed again. Preview buttons never save decisions or invoke an AI/RAG service.

## Verification

With the local app running, run `node tests/vehicle-demo.mjs`. It checks feature mapping, priority precedence, actual mesh dimensions/seat transforms, WebGL rendering, unchanged tabs, concept/reset controls, requirement-to-component focus, G60-only support, a mobile viewport, approval persistence after reload, and Baseline/After comparison. Approval tests use a disposable SQLite backup; the reviewer database is not modified. `pytest tests/test_vehicle_design.py` checks persistence, cohort boundaries and withdrawal/invalidation. Set `PLAYWRIGHT_EXECUTABLE_PATH` for another installed Chromium binary. The default is the project-local test browser. Test screenshots and temporary compiled helpers stay under ignored `.local/vehicle-check`.

TypeScript and the browser/geometry checks passed locally. A production build passed with `npm run build -- --webpack`; the default Turbopack build could not bind its CSS compiler socket in this environment.
